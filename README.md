## What make.fun is

make.fun is a competition platform for software bounties. Each bounty explains what to build and how entries are evaluated.

People can work with AI coding agents to create and submit entries.

An entry is usually a public code repository plus records of the AI sessions that built it.

The exact entry requirements depend on the bounty.

Automatic checks verify required files and other listed conditions. Passing entries are graded using the bounty's published method.

The leaderboard shows the current standings for the competition.

The final ranking is set after the bounty closes and evaluation is complete.

Rewards are offered for the places listed on the bounty page.

An entry that does not finish in a paid place does not receive a bounty reward.

Most bounties are free to enter.

Any entry fee is shown on the bounty page before you enter.

Rewards are claimed by winners in USDC on Solana.

Winning is not guaranteed, and the amount of work does not by itself determine a result.

## How bounties work

A bounty is a time-limited challenge with a defined goal.

The page explains what to build and submit, when entries close, and how results are decided.

The page may also list a reward total, individual paid places, technical requirements, or an entry fee.

Read the whole page before deciding to participate.

### The typical journey

1. Find a bounty that is open for entries.
2. Read its brief, eligibility rules, entry requirements, and deadline.
3. Prepare the software and supporting files requested by that bounty.
4. Submit the entry in the format the bounty accepts.
5. Review automated checks and fix any issues they report.
6. Wait for the final judging and published result.
7. If your entry wins a reward, claim it through your account.

Some details vary from one bounty to another.

For example, a bounty may require a specific language, public repository, screenshot, or session transcript.

Never assume one bounty's checklist applies to all the others.

### How judging works

The bounty page explains its scoring metric or evaluation process.

Automatic checks can verify that an entry follows submission rules.

The grader evaluates entries using the method described for that competition.

The displayed standings can be provisional while the competition remains open.

The final ranking is the one that determines which places receive the listed rewards.

Tie-breaking and special evaluation details, when applicable, are described by the bounty.

Treat the written bounty rules as the source of truth for that particular challenge.

## What you need

Before you begin, gather the basics below.

### An account

You need to sign in to make.fun to enter and track your work.

Use an account you can access throughout the competition.

If a bounty requires a linked account or profile, complete that requirement before preparing your entry.

### A computer and an internet connection

You need a way to read the bounty, download its kit when provided, and upload your entry.

Some kits need tools such as Git, Node.js, Python, or another runtime.

Install only the tools the bounty or kit instructions actually request.

### A coding agent, if you want one

An AI coding agent can help you plan, write, and improve software.

You can use an agent supported by the kit or another workflow accepted by the bounty.

Keep the working session available if the entry rules require session records.

You remain responsible for checking that the result matches the brief.

### A place to store your work

Many bounties ask for a public GitHub repository.

If GitHub is required, make sure you can create a repository and push files to it.

Some bounties may accept another submission format, so confirm the requirements first.

### A Solana wallet for rewards

If you win, the reward is claimed in USDC on Solana.

Be ready to use a wallet you control when the account asks you to claim.

Never share a wallet's recovery phrase or private key with another person or in a public repository.

### Time to read and test

Set aside time to understand the brief before building.

Leave time for checking files, addressing feedback, and submitting before the deadline.

## Step 3: Get the kit

When a bounty provides a kit, use the download link or instructions on that bounty's page.

The kit is a starter package of instructions or tools for preparing and checking an entry.

The contents differ between bounties.

Read the kit's README and any rules or setup notes before running commands.

Check the required runtime versions and install the needed dependencies.

Keep the downloaded kit in a dedicated working folder.

Do not edit a starter file until you understand whether the task expects you to preserve it.

For a command-line workflow, copy commands carefully and run them from the specified directory.

If a command fails, read the error and compare your setup with the kit's requirements.

Use the bounty's own kit and instructions rather than assuming that a different competition's kit is interchangeable.

If the bounty does not provide a kit, follow the submission instructions on its page.

## Step 4: Build an entry

### Start with a small plan

Write down the main requirements in your own words.

Separate required behavior from optional improvements.

Choose a first version that can satisfy the core task.

Plan how you will verify each important requirement.

Keep the deadline in view as you decide what to add.

### Work in a clear project folder

Create or open the repository you plan to submit.

Use filenames and folders that make the project easy to understand.

Keep required files at the locations stated by the bounty.

Avoid adding unrelated files that make the entry confusing.

If the project needs setup instructions, document the necessary steps in its README.

### Use an AI agent thoughtfully

Give your coding agent the task brief and the relevant rules.

Ask it to outline its plan before large changes.

Work in manageable steps so you can inspect the result as it develops.

Review important code and content instead of accepting every generated change automatically.

Ask for tests or checks that match the actual requirements.

Keep your agent's working session and transcripts when the bounty requires them.

Do not fabricate or edit session records to make them appear to show work that did not happen.

If the kit provides a way to bundle session records, follow its directions.

### Build for the stated task

Prioritize the specific goal in the bounty brief.

Make the main user path work before polishing optional details.

Use examples and defaults that help someone understand the entry.

Handle expected errors in a clear and useful way.

Avoid unnecessary dependencies when a simpler solution will do.

Do not include credentials, private keys, or other secrets in the source files.

Do not commit personal or private information unless it is specifically required and appropriate.

### Test your work

Run the tests and local checks available for the project.

Use the kit's local grader when one is provided.

Check that the project starts or builds as the bounty expects.

Test the important user flows rather than only checking that files exist.

Review logs and errors before you decide that the project is ready.

If you change the project after testing, run the relevant checks again.

## Step 5: Submit your entry

Return to the bounty page and use its submission instructions.

Confirm the account shown is the account you intend to enter with.

Choose the repository or other deliverable requested by that bounty.

Make sure the submission points to the final version you intend to have judged.

Include every required file and any required session records.

If you are asked for a repository commit, follow the bounty's instructions about which commit is submitted.

Check that a required repository is public and can be opened without your login.

Remove secrets and accidental personal data before making a repository public.

Review the submission form before you send it.

Submit early enough to address a failed check before the deadline.

Wait for the page to confirm that the submission was received.

Save the entry link or identifier so you can find its status again.

## Step 6: Check your entry and resubmit

After submission, open the entry status page from the bounty or your account.

Read each check result rather than relying only on an overall status label.

When a check fails, read the reason and the suggested fix.

Compare the failed check with the bounty's stated requirements.

Make the needed correction in your project.

Run the relevant local tests or kit checks again.

Submit the corrected version using the bounty's resubmission process.

Check the new submission status to confirm it was received.

Resubmission is available only under the rules and before the deadline shown for that bounty.

Do not assume an earlier submission will be replaced unless the page confirms how it works.

If a check is unclear, use the bounty's discussion or contact route when one is available.

Keep a record of what you changed so you can avoid repeating the same mistake.

## Step 7: Claim rewards

Wait for final judging and the published result.

If your entry finishes in a paid place, open its result or reward details.

Follow the claim steps shown in your account.

Rewards are claimed in USDC on Solana to a wallet you control.

Make sure the destination wallet is correct before confirming a claim.

A claim may require an additional check or information requested by the platform.

Read any status message if a reward is held or not yet claimable.

Keep the claim confirmation and transaction details for your records.

If your entry does not place in a paid position, there is no bounty reward to claim for that entry.

Never pay someone who promises to turn an unclaimed reward into a guaranteed win.

## Tips for doing well

### Understand the evaluation

Build for the actual metric described on the bounty page.

Turn the evaluation criteria into a practical checklist before coding.

Do not optimize for popularity when the bounty uses an automated score, or the reverse.

### Make the core experience reliable

Ensure the primary feature works from a clean setup.

Remove avoidable crashes and confusing failure states.

Use sensible defaults so a reviewer can understand the project quickly.

### Leave time for verification

Reserve time for local runs, screenshots, documentation, and submission checks.

Do not wait until the final moments to upload a large repository or required artifact.

### Keep the submission easy to inspect

Use a clear project README and descriptive filenames.

Explain how to run the project and what it is intended to do.

Make required evidence easy to locate.

### Iterate carefully

Use feedback from checks to improve the work.

After each important change, rerun the tests that cover it.

Prefer a stable, complete entry to a collection of unfinished features.

### Protect your accounts

Keep account passwords, wallet recovery phrases, and private keys private.

Check the destination and network before approving wallet actions.

Do not put API keys or credentials in a public repository or an entry artifact.

## Tips for your first entry

1. **Choose a focused bounty.** Pick a task whose requirements and tools fit your available time.
2. **Turn the brief into a checklist.** Track each required feature, file, and proof item as you work.
3. **Get a small version running early.** Confirm the basic setup works before adding optional polish.
4. **Save work in clear milestones.** Use descriptive commits or backups so you can recover a known-good version.
5. **Test from the reviewer's perspective.** Follow the documented setup steps and try the main user flow from a clean start.
6. **Submit with time to spare.** Confirm the status page received your entry and fix any reported issues before closing.

## Frequently asked questions

### Is make.fun a job?

No. A bounty is a competition with its own requirements and rewards.

There is no guaranteed payment for entering or for spending a particular amount of time.

### Do I have to be an experienced programmer?

You can start as a newcomer, especially if you use a coding agent and choose an approachable task.

You should still review the result, understand what you are submitting, and test it.

### Do I need an AI coding agent?

People can work with AI coding agents on make.fun bounties.

Follow the specific bounty's requirements for tools and session records.

### Does it cost money to enter?

Most bounties are free to enter.

A bounty with an entry fee says so on its page, so check before submitting.

Your own development tools or model usage may have separate costs.

### What does the kit do?

A bounty kit provides files, tools, or guidance for preparing an entry.

Its exact features depend on the bounty.

### Can I submit work without GitHub?

It depends on the bounty.

If the bounty requires a public GitHub repository, you need to provide one that meets that requirement.

Check the entry instructions before building around a different format.

### Can I submit more than once?

Some bounties allow resubmissions before the deadline.

Use the entry status and instructions for that specific bounty to understand its limits.

### What happens if I miss the deadline?

The page may stop accepting entries when the deadline passes. Check the bounty's time zone and submit early; any exceptions or late-entry rules are specific to that bounty.

If you already submitted, whether you can still make changes or resubmit depends on its rules.

### Can I update my entry after submitting?

Follow the bounty's resubmission process. Pushing a new repository commit may not automatically update the version attached to your entry.

Check the entry page to confirm which version was received.

### Do I need a wallet to start?

You need a wallet you control to claim a reward if you win. Check the bounty and account prompts for any additional requirements before entering.

### Can I enter as part of a team?

Team and collaborator rules vary by bounty. Check its eligibility and submission requirements to see who may contribute and which account should submit.

### Why did my entry fail a check?

The check status should explain what requirement was not met.

Fix the named issue, run the relevant checks again, and resubmit if the bounty still accepts entries.

### When is the final result available?

The bounty page shows its deadline and status.

Final judging happens after entries close, and timing can differ between competitions.

### How do I get paid?

Winners claim the reward shown for their paid place through make.fun.

Rewards are paid in USDC on Solana to a wallet you control.

### What if I do not win?

You can review your result, learn from the evaluation, and use that experience on another open bounty.

An entry outside a bounty's paid places does not receive its listed reward.

### Where can I ask a question?

Start with the bounty page and its discussion or support links.

For general platform information, visit the make.fun site and its help resources.
